## Основные абстракции
#### POD: 
Наименьшая управляемая единица в Kubernetes, которая может содержать **один или несколько контейнеров**.

#### ReplicaSet: 
Объект, который гарантирует запуск определенного количества реплик подов.

#### Deployment: 
Объект, выполняющий ту же задачу, что и ReplicaSet с дополнительным функционалом версионирования(откаты и истории).

#### Service:
способ "публикации" пода или группы подов внутри и вовне кластера.

#### Namespace:
Логически разделенное пространство в кластере, которое используется для организации и изоляции ресурсов.

#### Ingress:
Объект, который управляет доступом к сервисам в кластере Kubernetes **снаружи**. Он предоставляет возможности маршрутизации HTTP и HTTPS трафика, позволяя определить правила, как запросы должны направляться на различные сервисы.

## Управление конфигурацией

#### ConfigMap:
Объект, используемый для разделения конфигурационных данных от контейнеров.

#### Secret:
объект, используемый для хранения конфиденциальной информации, такой как пароли, токены доступа и другие чувствительные данные.

===============================================================

## Хранение данных

#### PersistentVolume:
Абстракция, представляющая хранилище данных в кластере Kubernetes

#### PersistentVolumeChain:
Запрос от пользователя на предоставление доступа к PersistentVolume

#### Storage Class:
Абстракция, которая определяет "класс" хранилища, предоставляемый администратором кластера. Он позволяет динамически создавать Persistent Volume (PV) с заданными параметрами хранения, такими, как тип диска (например, SSD или HDD), зона доступности, параметры производительности и т.д.

===============================================================

## Управление кластером

#### Node:
Физический или виртуальный сервер, на котором запускаются поды (aka Data Plane)

#### Cluster:
Группа узлов, которые работают вместе. Включает в себя мастер-узлы и рабочие группы.

#### Control Plane:
Набор компонентов, которые отвечают за управление состоянием кластера. Он координирует все операции в кластере и включает следующие ключевые компоненты:
1. kube-apiserver: предоставляет интерфейс для взаимодействия с кластером через API.
2. etcd: распределенное хранилище, которое сохраняет все данные о состоянии кластера.
3. kube-scheduler: отвечает за распределение новых подов на узлы в кластере на основе доступных ресурсов и других ограничений.
4. kube-controller-manager: управляет различными контроллерами, которые следят за состоянием объектов в кластере и предпринимают действия для поддержания желаемого состояния.

===============================================================

## Контроллеры

#### Ingress Controller:
Компонент, который управляет входящим сетевым трафиком и предоставляет функции маршрутизации.

#### Gateway Controller:
Компонент, который управляет объектами Gateway API, обеспечивая контроль и настройку сетевого трафика. Gateway API предоставляет **расширенные возможности маршрутизации трафика** и гибкость управления, превосходя традиционные возможности Ingress.

## Проверки и ресурсы

#### <span style="color:rgb(66, 170, 255)">Probe</span>: 
Механизм для проверки состояния контейнера или приложения внутри пода. Пробы можно разделить на три типа:

1.  <mark style="background: #BBFABBA6;">Liveness Probe</mark>:
     - *Определение*: Проверяет, жив ли контейнер. Если контейнер не проходит проверку liveness probe, Kubernetes перезапускает его.
     - *Использование*: Чтобы удостовериться, что контейнер не застрял и продолжает функционировать.
2. <mark style="background: #BBFABBA6;">Readiness Probe</mark>:
     - *Определение*: Проверяет, готов ли контейнер принимать трафик. Если контейнер не проходит проверку readiness probe, Kubernetes исключает его из списка подов, к которым могут направляться запросы.
     - *Использование*: Чтобы удостовериться, что контейнер готов обрабатывать запросы перед тем, как трафик будет направлен на него.
3. <mark style="background: #BBFABBA6;">Startup Probe</mark>:
     - *Определение*: Используется для проверки того, что контейнер **успешно запустился**. Если контейнер не проходит проверку startup probe, Kubernetes перезапускает его. Эта проба полезна для приложений с длительным временем запуска.
     - *Использование*: Чтобы удостовериться, что контейнер полностью запустился перед началом проверки liveness и readiness.


#### <span style="color:rgb(60, 170, 255)">Виды Probe</span>:

- <mark style="background: #BBFABBA6;">HTTP GET Probe</mark>:
     Выполняет HTTP GET запрос к указанному эндпоинту контейнера. Если возвращаемый код состояния находится в диапазоне 200-399, проба считается успешной.
- <mark style="background: #BBFABBA6;">TCP Socket Probe</mark>:
     Пытается установить TCP-соединение с контейнером по указанному порту. Проба успешна, если соединение установлено.
- <mark style="background: #BBFABBA6;">Exec Probe</mark>:
     Выполняет указанную команду внутри контейнера. Если команда завершается с кодом 0, проба считается успешной.
- <mark style="background: #BBFABBA6;">gRPC Probe</mark>:
     Реализует пробу через gRPC healthchech протокол для приложений, поддерживающих этот протокол.

<mark style="background: #ADCCFFA6;">Resource Limits</mark>:
     Установка ограничений на ресурсы, такие как CPU и память, используемые подами. При достижении лимита K8S принудительно "убивает" под.

<mark style="background: #ADCCFFA6;">Resource Requests</mark>:
     Механизм, который позволяет определить минимальные ресурсы (CPU и память), которые необходимы контейнеру для его работы. Используемые Scheduler, для размещения пода в кластере.

# Метки, размещение и селекторы.

#### Label:
     Ключевое слово или пара ключ-значение, присваиваемая объектам Kubernetes для их идентификации и организации.

#### Annotation:
     Механизм для добавления метаданных к объектам Kubernetes.

#### Affinity:
     Механизм для указания предпочтительных или нежелательных узлов для развертывания подов.

#### Taints and Tolerations:
     Механизм для указания предпочтений и ограничений по размещению подов на узлах.

#### Node Selector:
     Способ назначения подов на узлы с определенными метками. Он позволяет ограничить 
     выполнение подов только на тех узлах, которые соответствуют заданным критериям.
