Независимо от того, каким образом мы управляем кластером Kubernetes, все запросы будут поступать в Kubernetes **API - центральный вход в Kubernetes.** С API взаимодействуют все, в том числе **Kubernetes Master** ( под Kubernetes Master подразумеваем совокупность управляющих компонентов. В самом Kubernetes такого термина нет). Kubernetes Master обращается к API для того, чтобы понимать, какую работу надо сделать, посмотреть статус, что-то запросить, поменять и так далее.

Часть кластера Kubernetes - серверы кластера, его **nodes** ( ноды ), на которых происходит запуск приложений.
#### Работа с приложениями в Kubernetes

Если произойдет глобальная авария, Kubernetes поймет, к какому состоянию нужно привести свою инфраструктуру, какие приложения были запущены до отключения, где все хранится и так далее. Для этого у него есть **storage** ( хранилище )

![[Pasted image 20260615182820.png]]

Разберём на примере взаимодействие компонентов. Представим, что мы хотим запустить приложение, используя YAML-манифест и kubectl в кач-ве инструмента управления. Готовим текстовый файл с информацией о том, что есть приложение app, которое должно запуститься из image:myimage в двух репликах. С помощью утилиты kubectl применяем или отправляем файл на запуск, на конфигурирование внутрь кластера Kubernetes.

Файл поступает в API, который пытается сохранить файл в storage. Он его сохранит, чтобы понимать целевое состояние кластера Kubernetes.

Если мы хотим видеть приложение в двух репликах, значит, целевое состояние изменилось. Даже в случае аварии мы должны будем запустить приложение в двух репликах, потому что мы записали это в хранилище storage.

Далее в работу вступает Kubernetes Master. У компонентов, которые находятся внутри мастера, много различных функций. Один из компонентов решает, на каких нодах нужно запустить приложение.

![[Pasted image 20260618151315.png]]

Напр, мастер решает запустить первую реплику приложения на ноде 1, а вторую - на ноде 3. Спустя некоторое время команды применяются и на ноде 1 появляется первая реплика, на ноде 3 - вторая реплика.

![[Pasted image 20260618151433.png]]

Теперь мы хотим, чтобы приложение работало в трёх репликах. Меняем в текстовом файле цифру 2 на 3, затем с помощью kubectl его применяем. Файл снова отправляется в API. API его перезаписывает в хранилище. Мастер понимает, что произошло изменение: теперь нужно не две реплики приложения, а три. Он решает, что третью реплику нужно запустить на ноде 4.
