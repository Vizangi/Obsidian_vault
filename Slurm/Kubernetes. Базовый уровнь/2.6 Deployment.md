Является родительским объектом по отношению к репликасету, что позволяет использовать весь функционал репликасетов и подов. Деплоймент **может управлять релизами приложений**


```markup
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: my-app
  strategy:
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
    type: RollingUpdate
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - image: nginx:1.12
        name: nginx
        ports:
        - containerPort: 80
```

#### Стратегии обновления: Rolling Update и Recreate

В рамках секции `strategy` мы описываем процесс обновления или отката приложения. Это то, что отличает деплоймент от остальных абстракций. Деплоймент поддерживает две стратегии обновления. Стратегия **recreate** - направлена на то, чтобы удалить всё старое и сразу запустить новое. Поды старой версии будут удаляться, а поды новой версии - стартовать. Удобно этим пользоваться на тестовых окружениях, там, где важна не доступность, а скорость. Стратегия **rollingUpdate** призвана постепенно обновлять или откатывать приложение. Это более приближенный к проду вариант использования.

Остановимся подробнее на rollingUpdate. Есть две реплики, то в зависимости от настроек они будут обновляться постепенно, например по одной. Если количество реплик больше, можно сделать так, чтобы они обновлялись в процентном соотношении. Например, для 10 реплик можно задать такие настройки: 50% обновляем первым шагом, оставшиеся 50% - следующим. Задавать количество реплик и процент для обновления можно с помощью параметров `maxSurge` и `maxUnavailable`.

В `maxSurge` указываем, какое количество реплик будет запущено дополнительно к исходному. Зададим параметр `maxSurge: 1`. Если у нас 2 реплики, то запустится еще одна, уже с новой версией приложения. Две реплики продолжают работать со старой версией приложения, а третья в процессе обновления запускается уже с новой версией.

В `maxUnavailable` указываем количество реплик, которые могут быть отключены во время процесса обновления. Есть две реплики приложения текущей версии, мы указываем `maxUnavailable: 1`, то есть позволяем отключить одну реплику со старой версией в процессе обновления.

 
```markup
 rollingUpdate:
      maxSurge: 1
      maxUnavailable: 1
    type: RollingUpdate
```

Прописываем тип настройки.

Когда деплоймент начнет обновляться, то:
- дополнительно запуститься одна реплика нового приложения
- параллельно будет отключаться одна реплика старой версии приложения.

Когда этот шаг завершится, всё повторится. Еще одна реплика запустится с новой версией, ещё одна реплика со старой версией будет погашена и так далее.

#### Функциональность деплоймента.

##### **apply**

Версии можно обновлять, и они должны обновляться очень плавно. В deployment.yaml обновим старую версию `ngixn` (1.12) до 1.26
```markup
spec:
      containers:
      - image: nginx:1.26
        name: nginx
        ports:
        - containerPort: 80

kubectl apply -f deployment.yaml
my-deployment configured 
kubectl get po
```

появились новые поды (возраст 17 секунд)

`kubectl describe po my-deployment-84ff997cdd-r27st`

У `describe` есть секция `events`, где можно посмотреть, какие события происходили с этим объектом. В том числе здесь можно увидеть ошибки, связанные с данной абстракцией.

Нас интересует поле `image`. Видим версию `nginx 1.26`. Под и правда обновился, причем очень быстро.

##### **rollout**

Для отката версии приложения можно воспользоваться командой _rollout_

```
kubectl rollout history deploynment my-deployment
```

![[Pasted image 20260907182205.png|383]]

Есть три "ревизии" (REVISION), три варианта отката версии приложения. Логично: один раз мы запустили деплоймент и два раза его обновили.

В рамках деплоймента есть возможность откатиться на версию назад. Для того, чтобы понять, как это реализуется, нужно посмотреть, какие сейчас есть репликасеты.

```
kubectl get rs
```

![[Pasted image 20260907185223.png]]

Деплоймент один, а репликасетов уже три: самый старый репликасет, чуть поновее и самый свежий. У самого свежего в полях `DESIRED, CURRENT и READY` значения 2. Это текущий репликасет. У остальных по нулям. Это репликасеты, связанные с прошлыми версиями приложения. Выполним команду `describe` и выберем самый старый репликасет.

```
kubectl describe rs my-deployment-bc66f6dc | grep Image
```

_my-deployment-bc66f6dc_ — имя репликасета.

![[Pasted image 20260907185821.png|453]]

Действительно, это та самая старая версия image 1.12 (которую обновляли до 1.26, а затем до 1.26.1)

выполним откат: 

```
kubectl rollout undo deploy my-deployment --to-revision=1
```

С помощью --to-revision можно выбрать, на какую именно версию назад необходимо откатиться. По умолчанию происходит откат на прошлую версию( nginx 1.26). Если хотим откатиться на первоначальную версию 1.12, нужно указать 1. Отсчет начинается с нуля, поэтому  прошлая версия - "нулевая", а для позапрошлой значение будет 1.

```

```
